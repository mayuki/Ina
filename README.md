# Ina

**Ina** (**I**L to **NA**tive) compiles a .NET application into a native executable
*without a native toolchain*: no clang, gcc, `ld`, MSVC, Windows SDK or sysroot of the
target system is needed, which makes cross compilation a matter of passing `--os` and
`--arch`.

```console
$ dotnet build -c Release samples/HelloWorld
$ ina samples/HelloWorld/bin/Release/net11.0/HelloWorld.dll --os linux --arch x64
HelloWorld.dll -> /work/HelloWorld (1.3 MB, linux-x64, .NET 11.0.0, glibc 2.25+, compile 1.3s, link 0.13s)
$ ./HelloWorld
Hello, World!
$ ina samples/HelloWorld/bin/Release/net11.0/HelloWorld.dll --os windows --arch x64
HelloWorld.dll -> /work/HelloWorld.exe (1.1 MB, win-x64, .NET 11.0.0, compile 1.3s, link 0.10s)
```

> **Status: proof of concept.** Linux executables for x64 and arm64 and Windows executables
> for x64 work, including cross compilation between all of them: from the same assemblies,
> a Windows executable built on Linux is byte-identical to the one built on Windows. Windows
> on arm64 is implemented but has not been run on real hardware. See [Status](#status) for
> what is and is not covered.

## How it works

Ina borrows code generation from .NET itself and replaces the one step that ties
NativeAOT to a native toolchain: the link.

```
App.dll + dependencies
   │
   │  1. resolve packs    ILCompiler (host) and the NativeAOT runtime pack (target),
   │                      reused from the NuGet cache or downloaded from nuget.org
   ▼
   │  2. compile          ILCompiler (RyuJIT) turns IL into an object file for the target
   ▼
App.o   + libRuntime.WorkstationGC.a + libSystem.Native.a + ...      (Linux: ELF objects)
App.obj + Runtime.WorkstationGC.lib + aotminipal.lib + ...           (Windows: COFF objects)
   │
   │  3. link             Ina.Linker, two linkers written in C#, produces the executable
   ▼
App      (ELF, dynamically linked against the C library only)
App.exe  (PE32+, importing system DLLs and the Universal C Runtime only)
```

The linkers do not need the libraries of the target system either. They link against an
*import table*: the names (and for glibc the versions) of the symbols that the system
libraries export, stored as text. The pieces that a toolchain links statically into every
program are generated by the linker: for Linux the startup code of `crt1.o` and the handful
of functions from `libc_nonshared.a`, for Windows the startup code, the stack probe, the
stack protection and the thread-local storage support of the Visual C++ runtime. This is
the same idea that lets Go cross compile out of the box.

A side effect is portability. A Linux executable built on a current distribution only
requires the glibc 2.27 baseline (in practice symbols up to 2.25), whereas the same
application published with NativeAOT on Ubuntu 24.04 requires glibc 2.34. A Windows
executable depends on nothing but DLLs that are part of Windows 10 and later; it does not
need the Visual C++ redistributable.

[docs/Design.md](docs/Design.md) explains the design, the alternatives that were
considered and the internals of the linkers.

## Usage

Requirements: the .NET 11 SDK, and access to nuget.org the first time a target is
used (the packs are cached afterwards).

```console
$ dotnet build                                   # builds ina into src/Ina/bin
$ dotnet src/Ina/bin/Debug/net11.0/ina.dll --help
```

`ina` can also be packaged and installed as a local .NET tool (a package of about 500 KB):

```console
$ dotnet pack src/Ina -c Release -o artifacts
$ cd ../MyApp && dotnet new tool-manifest
$ dotnet tool install Ina --add-source ../Ina/artifacts --version 0.1.0
$ dotnet ina bin/Release/net11.0/MyApp.dll
```

`ina` takes the application assembly as produced by `dotnet build` (framework-dependent
output is what you want; the dependencies next to it are picked up automatically).

```
ina <assembly> [options]

  -o, --output <path>         Path of the executable [default: the assembly name in the current directory,
                              with .exe for Windows]
  --os <linux|windows>        Target operating system [default: the system of this machine if it is one of
                              them, otherwise linux]
  --arch <x64|arm64>          Target architecture [default: the architecture of this machine]
  -O, --optimize <mode>       blended, speed, size or none [default: blended]
  --runtime-version <ver>     Version of the .NET runtime packs [default: newest patch of the app's framework]
  --invariant-globalization   Do not depend on ICU at run time
  --symbols                   Keep a symbol table in the executable (Linux targets only)
  --no-pie                    Produce a fixed-address executable
  --intermediate-dir <dir>    Directory for the object file and the compiler response file
  -v, --verbose               Show phases, timings and compiler output
```

Cross compiling, for another architecture and for another operating system:

```console
$ ina bin/Release/net11.0/App.dll --arch arm64 -o App-arm64
App.dll -> /work/App-arm64 (1.3 MB, linux-arm64, .NET 11.0.0, glibc 2.25+, compile 1.2s, link 0.12s)
$ ina bin/Release/net11.0/App.dll --os windows
App.dll -> /work/App.exe (1.1 MB, win-x64, .NET 11.0.0, compile 1.2s, link 0.10s)
```

An application that was built as a graphical Windows application (`OutputType=WinExe`)
becomes an executable for the Windows subsystem, which starts without a console window.

Environment variables: `INA_PACKS` (pack cache, default `~/.ina/packs`),
`INA_NUGET_SOURCE` (NuGet v3 flat container to download packs from),
`NUGET_PACKAGES` (the NuGet global packages folder is reused read-only).

The application is compiled the way `PublishAot` compiles it, so the same rules apply:
no runtime code generation, reflection only where the compiler can see it, and
`System.Text.Json` through source generation (see `samples/JsonReader`).

## Status

| | |
|---|---|
| Targets | `linux-x64`, `linux-arm64` (glibc), position independent or fixed-address executables; `win-x64`, `win-arm64` (Windows 10 and later), relocatable or fixed-address executables |
| Hosts | Anywhere ILCompiler runs. Developed and tested on `linux-x64` and `win-x64`; other hosts are untested |
| Frameworks | Applications that target .NET 10 or .NET 11; each is compiled with the packs of its own version. The tool itself runs on .NET 11 |
| Verified | Console apps, multi-assembly apps, `System.Text.Json`, exceptions, GC, threads and tasks, thread statics, file I/O, sockets, HTTPS, compression, crypto (OpenSSL on Linux, the system providers on Windows) |
| Cross compilation | Linux to Windows and Windows to Linux, x64 to arm64. Given the same assemblies, Windows executables built on Linux and on Windows are byte-identical |
| Self-hosting | `ina` compiles itself for Linux and for Windows: the native `ina` builds applications for both systems, and rebuilding itself with it yields a byte-identical executable |

Not done yet:

- **Running `win-arm64` executables.** They are linked, checked structurally and their
  generated code is executed in an emulator by the tests, but no Windows on ARM64 machine
  was available
- macOS (Mach-O) targets, and fully static musl executables
- Debug information: the compiler's DWARF output is dropped for Linux, and no program
  database (PDB) is written for Windows
- Windows security mitigations that need linker support: Control Flow Guard tables and the
  CET shadow stack marker. The executables run without them, like a NativeAOT application
  that opts out of both
- Satellite resource assemblies, ASP.NET Core and other shared frameworks
- Native libraries of NuGet packages (only the framework's own native code is linked)
- Integration into `dotnet publish`

Verification gaps are listed in [docs/Design.md](docs/Design.md#8-verification).

## Development

```console
$ dotnet build
$ dotnet test          # ~260 tests, about a minute
```

The tests do not use a native toolchain: object files are assembled in memory by test
helpers, linked, and executed. What can be executed depends on the machine:

| Executables for | are run |
|---|---|
| `linux-x64` | on x64 Linux; the linker tests also on Windows through WSL when a distribution is installed |
| `linux-arm64` | on arm64 Linux, or with `qemu-aarch64` and the C library from `/usr/aarch64-linux-gnu` (Debian/Ubuntu: `apt install qemu-user libc6-arm64-cross`) |
| `win-x64` | on x64 Windows |
| `win-arm64` | never as a whole; the code that the linker generates runs in an emulator that is part of the tests |

Tests whose executables can not be run are skipped; the tests that inspect the structure
of the produced images run everywhere. The first run of the end-to-end tests downloads the
ILCompiler and runtime packs.

## Third-party components

Ina does not redistribute any of these; they are downloaded from nuget.org when needed.

- [ILCompiler](https://www.nuget.org/packages/runtime.linux-x64.Microsoft.DotNet.ILCompiler)
  and the [NativeAOT runtime packs](https://www.nuget.org/packages/Microsoft.NETCore.App.Runtime.NativeAOT.linux-x64)
  (.NET Foundation, MIT)
- For Windows targets additionally [Microsoft.DotNet.ILCompiler](https://www.nuget.org/packages/Microsoft.DotNet.ILCompiler),
  for its list of Windows APIs that may be called directly (.NET Foundation, MIT)

The import tables in `src/Ina.Linker/Abi/Tables` are interface facts; no code from the
libraries is included:

- `glibc-*.abi` list symbol names and symbol versions exported by the GNU C library 2.27,
  extracted with `eng/generate-abi.sh`.
- `windows.abi` lists which system DLL of Windows exports which name, extracted from the
  export tables of the DLLs with `eng/GenerateWindowsAbi.cs`. Neither the Windows SDK nor
  the Visual C++ libraries are used, at build time or to generate the table.
