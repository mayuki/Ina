# Ina

**Ina** (**I**L to **NA**tive) compiles a .NET application into a native executable
*without a native toolchain*: no clang, gcc, `ld`, MSVC, Xcode, SDK or sysroot of the
target system is needed, which makes cross compilation a matter of naming the target.

It plugs into `dotnet publish`, where it takes the place of NativeAOT's native link:

```console
$ dotnet publish -r linux-arm64        # a project with <PublishIna>true</PublishIna>, on an x64 machine
  App -> /work/App/bin/Release/net10.0/linux-arm64/App.dll
  Generating native code
  Linked App with Ina (1.4 MB, linux-arm64, glibc 2.17+)
  App -> /work/App/bin/Release/net10.0/linux-arm64/publish/
```

and it is a command of its own for an assembly that is already built:

```console
$ dotnet build -c Release samples/HelloWorld
$ ina samples/HelloWorld/bin/Release/net10.0/HelloWorld.dll --os linux --arch x64
HelloWorld.dll -> /work/HelloWorld (1.2 MB, linux-x64, .NET 10.0.15, glibc 2.17+, compile 1.3s, link 0.13s)
$ ./HelloWorld
Hello, World!
```

The same command builds a macOS executable, on a Mac or anywhere else:

```console
$ ina samples/HelloWorld/bin/Release/net10.0/HelloWorld.dll --os macos --arch arm64
HelloWorld.dll -> /work/HelloWorld (1.2 MB, osx-arm64, .NET 10.0.15, macOS 12.0+, compile 0.6s, link 0.18s)
```

> **Status: proof of concept.** Linux and macOS executables for x64 and arm64 work,
> including cross compilation between all of them. See [Status](#status) for what is and
> is not covered.

## How it works

Ina borrows code generation from .NET itself and replaces the one step that ties
NativeAOT to a native toolchain: the link.

```
App.dll + dependencies
   │
   │  1. resolve packs    ILCompiler (host) and the NativeAOT runtime pack (target),
   │                      reused from the NuGet cache or downloaded from nuget.org
   ▼
   │  2. compile          ILCompiler (RyuJIT) turns IL into an object file for the target
   ▼
App.o + libRuntime.WorkstationGC.a + libSystem.Native.a + ...
   │
   │  3. link             Ina.Linker, a linker written in C#, produces the executable
   ▼
App  (ELF for Linux, Mach-O for macOS; dynamically linked against system libraries only)
```

With `dotnet publish`, steps 1 and 2 are those of the .NET SDK: NuGet restores the packs
and the NativeAOT targets run ILCompiler. With the `ina` command, Ina does them itself.
Step 3 is the same linker in both cases.

The linker does not need the libraries of the target either. It links against an
*import table*: the names of the symbols that the system libraries export, generated
once and shipped as data. For Linux that is glibc with its symbol versions, taken from
the oldest glibc that .NET supports; for macOS it is the C library (libSystem) and the
frameworks the .NET runtime uses, taken from the text-based stubs of the macOS SDK. What
a toolchain adds to every link on its own is generated by the linker: on Linux the
startup code of `crt1.o` and the handful of functions from `libc_nonshared.a`, on macOS
the Objective-C selector stubs, the version check of the compiler support library and
the ad-hoc code signature without which Apple silicon does not run a program. This is
the same idea that lets Go cross compile out of the box.

A side effect is portability: an executable built on a current distribution only
requires the glibc 2.27 baseline (in practice symbols up to 2.17), whereas the same
application published with NativeAOT on Ubuntu 24.04 requires glibc 2.34. A macOS
executable is bound the way Apple's linker binds for macOS 12, the oldest version the
.NET 10 runtime supports.

[docs/Design.md](docs/Design.md) explains the design, the alternatives that were
considered and the internals of the linker.

## Usage

Requirements: the .NET 10 SDK, and access to nuget.org the first time a target is
used (the packs are cached afterwards).

The application is compiled the way `PublishAot` compiles it, so the same rules apply
to both ways of using Ina: no runtime code generation, reflection only where the compiler
can see it, and `System.Text.Json` through source generation (see `samples/JsonReader`).

### Publishing a project with `dotnet publish`

`Ina.Sdk` is an MSBuild project SDK that is used in addition to the .NET SDK. A project
refers to it and sets `PublishIna`:

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <Sdk Name="Ina.Sdk" Version="0.1.0" />

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <PublishIna>true</PublishIna>
  </PropertyGroup>

</Project>
```

```console
$ dotnet publish                       # for this machine
$ dotnet publish -r linux-arm64        # for another architecture
$ dotnet publish -r osx-arm64          # for another operating system
```

The publish directory contains the executable and the content files of the project, as
with NativeAOT. `dotnet build` and `dotnet run` keep running the application on the
regular runtime.

`PublishIna` implies `PublishAot`, and that is the whole idea: the .NET SDK does what it
does for NativeAOT (analyzers, trimming, ILCompiler, the properties documented for
[Native AOT deployment](https://learn.microsoft.com/dotnet/core/deploying/native-aot/))
and Ina links the result. An application of `Microsoft.NET.Sdk.Web` is published the same
way (see `samples/MinimalApi`).

- The version of the SDK can also be given in `global.json`
  (`"msbuild-sdks": { "Ina.Sdk": "0.1.0" }`), with `<Sdk Name="Ina.Sdk" />` in the project.
- `PublishIna` can come from the command line instead: `dotnet publish -p:PublishIna=true`.
  `enable` is accepted as well as `true`.
- **As a package reference**, for example with central package management, `PublishAot`
  has to be set too. A package takes no part in the restore of the project that refers to
  it, so it cannot make the .NET SDK download the compiler:

  ```xml
  <PropertyGroup>
    <PublishAot>true</PublishAot>
    <PublishIna>true</PublishIna>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Ina.Sdk" Version="0.1.0" PrivateAssets="all" />
  </ItemGroup>
  ```

What differs from a NativeAOT publish, apart from not needing a toolchain:

| Setting | With `PublishIna` |
|---|---|
| `RuntimeIdentifier` (`-r`) | `linux-x64`, `linux-arm64`, `osx-x64` or `osx-arm64`, independent of the machine that publishes. Anything else is an error (INA1002). The Linux targets are tested on a `linux-x64` host, the macOS targets on an `osx-arm64` and a `linux-arm64` host; [Verification](docs/Design.md#8-verification) lists the combinations that were only built or not tried |
| `PositionIndependentExecutable` | `false` produces a fixed-address executable for Linux. macOS has none, so there it is an error (INA1003) |
| `StripSymbols` | `false` keeps the symbol table. There is no debug information, and no `.dbg` file or `.dSYM` bundle yet |
| `NativeLibrary`, `DirectPInvoke` | Static libraries are linked into the executable, as long as they need nothing but what the import table of the target lists: the C library, and for macOS the frameworks that the .NET runtime itself uses |
| `LinkerArg` | Ignored with a warning (INA1005): no native linker runs |
| `NativeLib`, `CustomNativeMain`, `StaticExecutable`, `StaticICULinking`, `StaticOpenSslLinking`, `LinkStandardCPlusPlusLibrary`, `UseSystemZlib`, `UseSystemBrotli` | Not supported (error INA1003) |

A macOS executable is signed ad hoc by the linker, like the ones of the `ina` command, so
it runs on the Mac it is copied to without further steps.

`Ina.Sdk` is not on nuget.org. To try it, pack it and add the folder as a package source:

```console
$ dotnet pack src/Ina.Sdk -c Release -o artifacts
$ dotnet nuget add source /path/to/Ina/artifacts --name ina
```

### Compiling an assembly with the `ina` command

```console
$ dotnet build                                   # builds ina into src/Ina/bin
$ dotnet src/Ina/bin/Debug/net10.0/ina.dll --help
```

`ina` can also be packaged and installed as a local .NET tool (a package of about 630 KB):

```console
$ dotnet pack src/Ina -c Release -o artifacts
$ cd ../MyApp && dotnet new tool-manifest
$ dotnet tool install Ina --add-source ../Ina/artifacts --version 0.1.0
$ dotnet ina bin/Release/net10.0/MyApp.dll
```

`ina` takes the application assembly as produced by `dotnet build` (framework-dependent
output is what you want; the dependencies next to it are picked up automatically).

```
ina <assembly> [options]

  -o, --output <path>         Path of the executable [default: the assembly name in the current directory]
  --os <linux|macos>          Target operating system [default: the system of this machine if it is one of them, otherwise linux]
  --arch <x64|arm64>          Target architecture [default: the architecture of this machine]
  -O, --optimize <mode>       blended, speed, size or none [default: blended]
  --runtime-version <ver>     Version of the .NET runtime packs [default: newest patch of the app's framework]
  --invariant-globalization   Do not depend on ICU at run time
  --symbols                   Keep a symbol table in the executable
  --no-pie                    Produce a fixed-address executable (Linux only)
  --intermediate-dir <dir>    Directory for the object file and the compiler response file
  -v, --verbose               Show phases, timings and compiler output
```

Cross compiling for arm64 on an x64 machine, and for an Intel Mac on a Linux machine:

```console
$ ina bin/Release/net10.0/App.dll --arch arm64 -o App-arm64
App.dll -> /work/App-arm64 (1.3 MB, linux-arm64, .NET 10.0.15, glibc 2.17+, compile 1.2s, link 0.12s)
$ ina bin/Release/net10.0/App.dll --os macos --arch x64 -o App-mac
App.dll -> /work/App-mac (1.3 MB, osx-x64, .NET 10.0.15, macOS 12.0+, compile 1.2s, link 0.12s)
```

macOS executables are ad-hoc signed by the linker, which is all macOS asks of a program
that is run from a terminal. An executable that is built on Windows has to be made
executable (`chmod +x`) after it has been copied to the Mac, because Windows file
systems do not record that.

Environment variables: `INA_PACKS` (pack cache, default `~/.ina/packs`),
`INA_NUGET_SOURCE` (NuGet v3 flat container to download packs from),
`NUGET_PACKAGES` (the NuGet global packages folder is reused read-only).

The command knows the base class library only. Applications that need a shared framework
such as ASP.NET Core are published with `dotnet publish`.

## Status

| | |
|---|---|
| Targets | `linux-x64`, `linux-arm64` (glibc), position independent or fixed-address executables; `osx-x64`, `osx-arm64` (macOS 12 and later) |
| Hosts | Anywhere ILCompiler runs. Developed and tested on `linux-x64`, `linux-arm64` and `osx-arm64`; Windows hosts are untested |
| Frameworks | .NET 10 and later (the NativeAOT runtime pack layout introduced with .NET 10) |
| Verified | Console apps, multi-assembly apps, `System.Text.Json`, exceptions, GC (workstation and server), threads and tasks, thread statics, file I/O, sockets, loopback HTTP and TLS, compression, crypto through OpenSSL (Linux) and through Apple's frameworks (macOS). With `dotnet publish` also an ASP.NET Core minimal API |
| Self-hosting | `ina` compiles itself, for Linux and for macOS: the native `ina` builds applications, and rebuilding itself with it yields a byte-identical executable |

macOS executables come out byte-identical whether they are built on Linux or on a Mac.
`osx-x64` executables have been compared instruction by instruction with what Apple's
linker produces from the same inputs, but they have not been run: see
[Verification](docs/Design.md#8-verification).

Not done yet:

- Windows (PE/COFF) targets, fully static musl executables, universal (fat) macOS binaries
- Debug information in the executable (the compiler's DWARF output is dropped; no dSYM)
- Native libraries (`NativeLib`) as output
- With the `ina` command: satellite resource assemblies, shared frameworks such as ASP.NET Core,
  and native libraries of NuGet packages. With `dotnet publish` the .NET SDK takes care of
  these inputs: ASP.NET Core is covered by a test, satellite assemblies and a static
  library were tried by hand

Verification gaps are listed in [docs/Design.md](docs/Design.md#8-verification).

## Development

```console
$ dotnet build
$ dotnet test          # ~320 tests, about a minute
```

The tests do not use a native toolchain: object files are assembled in memory by a
test helper, linked, and executed. The tests of the `dotnet publish` integration install
the `Ina.Sdk` package that the build has just produced and publish the samples with a
search path that contains nothing but `dotnet` and `sh`. Every test builds and inspects
its executable on any host; running it is skipped where the host cannot: Linux
executables need Linux (arm64 ones run under `qemu-aarch64` with the C library from
`/usr/aarch64-linux-gnu` when both exist; Debian/Ubuntu:
`apt install qemu-user libc6-arm64-cross`), macOS executables need a Mac of the same
architecture (x64 ones also run on Apple silicon with Rosetta).

The first run of the end-to-end tests downloads the ILCompiler and runtime packs, and
the runtime pack of ASP.NET Core.

### Trying `Ina.Sdk` without packaging it

The MSBuild files in `src/Ina.Sdk` are laid out as in the package, so a project can be
published with them straight from the source tree. Two properties take the place of the
reference to the package: one makes MSBuild import `Sdk.props`, the other points to the
link task in the build output instead of the `tasks` folder of the package.

```console
$ dotnet build src/Ina.Sdk
$ dotnet publish samples/MinimalApi -r linux-x64 \
    -p:PublishIna=true \
    -p:CustomAfterMicrosoftCommonProps=$PWD/src/Ina.Sdk/Sdk/Sdk.props \
    -p:InaTasksAssembly=$PWD/src/Ina.Sdk/bin/Debug/net10.0/Ina.Sdk.dll
$ samples/MinimalApi/bin/Release/net10.0/linux-x64/publish/MinimalApi
```

No file has to be changed for this, and the output goes to the `bin` and `obj` directories
of the sample, which Git ignores. Build `src/Ina.Sdk` again after a change to the linker
or the task.

A project outside of the repository does the same in its project file:

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <Import Project="/path/to/Ina/src/Ina.Sdk/Sdk/Sdk.props" />

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <PublishIna>true</PublishIna>
    <InaTasksAssembly>/path/to/Ina/src/Ina.Sdk/bin/Debug/net10.0/Ina.Sdk.dll</InaTasksAssembly>
  </PropertyGroup>

</Project>
```

This leaves out how NuGet resolves the SDK and how the package is laid out. The publish
tests cover both with the package itself.

## Third-party components

Ina does not redistribute any of these; they are downloaded from nuget.org when needed.

- [ILCompiler](https://www.nuget.org/packages/runtime.linux-x64.Microsoft.DotNet.ILCompiler)
  and the [NativeAOT runtime packs](https://www.nuget.org/packages/Microsoft.NETCore.App.Runtime.NativeAOT.linux-x64)
  (.NET Foundation, MIT)
- The link task is compiled against [Microsoft.Build.Utilities.Core](https://www.nuget.org/packages/Microsoft.Build.Utilities.Core)
  (Microsoft, MIT); at build time MSBuild provides its own copy

The import tables in `src/Ina.Linker/Abi/Tables` are interface facts; no code of any
library is included:

- `glibc-*.abi` list symbol names and symbol versions exported by the GNU C library 2.27,
  extracted with `eng/generate-abi.sh`.
- `macos-*.abi` list which system library of macOS exports which symbol, extracted with
  `eng/generate-macos-abi.sh` from the text-based stubs (`.tbd`) of Apple's macOS SDK:
  libSystem and the Objective-C runtime completely, the frameworks as far as the .NET
  runtime refers to them. The SDK is needed to regenerate the tables, never to use Ina.
